# 软件方案：准确性、一致性与交付证据

## 使用入口

在用户要求软件方案、需求设计、架构方案、需求对齐、架构评审、交付验收、梳理现有业务流程、前后台处理、状态机、业务规则或源码业务分析时（含现状说明）必须使用此模式，自动应用下述五项规则和需求到验收的追踪。默认输出精简中文 HTML（核心评审），保留可修改的 JSON 源及检查报告；明确要求完整技术方案时才展开全部技术章节。日常解释、幻灯片、现有 visual plan 等继续使用原有模式。

本模式覆盖通用 SKILL 的字体和交付规则：以最少内容呈现关键业务规则与异常路径；使用本地中文字体；使用本目录的 CLI 生成和检查。无需改写上游 kit、plan、Pi 或 MCP 实现。

## 业务逻辑优先与强制交付（先于排版）

1. **先确定意图与业务边界**：现状分析用 `businessFlow.intent=current`；提出变更用 `target`。每个场景标记 current 或 target，主路径必须符合本次意图。前端已开放、后端保留、拟实现、待确认分别说明，不把拟议决策当成现状。不同触发者或不同业务入口（例如客户取消与管理员关闭未受理订单）分别建路径，不画成一个无条件分支。
2. **先走完业务，再画图**：每个场景有触发角色、触发动作、入口条件、顺序步骤、结果类型和结果说明。正常、拒绝、待处理及失败路径按实际需求建模；异常条件必须具体，恢复或重试须重新核查资格。每一步引用规则、接口与状态迁移；每条路径关联自己的需求及验收。仅有数据库状态码、方法名称或技术名词不足以解释业务。
3. **状态对象独立**：区分订单、取消申请、外部处理结果和资金等各自生命周期；只为确实具有独立状态的对象建立模型，使用独立 DATA、实际 lifecycleField、STATE、TR。单张状态图只描述一个状态对象及一个阶段。每条路径声明各对象的起始/最终状态，逐步按 TR 演算；不得从未知状态、错误起点或终态凭空跳转。需要描述多对象关系时用场景内的状态对应关系，不混合为一个虚构状态。真实字段、条件和结果须以项目证据确认。
4. **跨视图同源**：流程图绑定场景，用 CLI `flow <design.json> --scenario SCN-id` 生成规范节点与箭头，把输出加入 diagrams；禁止另画不一致的箭头。时序图绑定场景，API 调用顺序与步骤一致；状态图标记 phase 并引用真实 TR。先确认路径与验收一致，再写评审结论。机械校验检查引用、顺序、状态连续性、结果和覆盖；自然语言、未建模的分支、真实源代码含义及业务完整性仍必须由 Agent 逐条复核，无法确认时列出待定。
5. **强制交付链路**：上述软件业务任务即使用户只说“梳理”“解释”“画流程图”，也必须读取本参考、构建带 businessFlow 的 design.json、validate、render、deliver。使用增强 CLI，禁止用普通 kit/render.mjs、手写 HTML、后处理或仅生成 Mermaid 代替。旧版 JSON 可继续通过旧校验，但新交付必须补充 businessFlow。执行 `deliver <实际HTML> --spec <实际JSON> --view compact`（完整模式 full；正式交付验收另加 --phase delivery），仅在返回 ok=true 后作为已检查的软件方案交付。报告必须与源和页面摘要绑定，普通 HTML、缺失报告、过期内容或不匹配视图都失败。门禁失败时修复模型并重渲染；如果工具不可用，明确报告阻塞，不降级成无检查的通用 HTML。浏览器不可用仅可标记 skipped 并给理由，业务验收独立记录。

数据契约及示例见 `software-design/CONTRACT.md` 与精简模板。精简页由规范场景直接生成业务主线，先展示所有主场景及 highlight=true 的关键异常，再补充未在路径表达的约束与待确认事项；路径正文计入原 800 字符预算。完整模型保留其他异常路径。严禁为压缩篇幅删去实际业务主线或重要异常条件。

## 表达规范（所有软件方案与聊天交付优先遵守）

充分分析、严格校验、精简交付。下面六条优先于篇幅、模板章节和通用排版建议；用户明确要求的内容以及事实准确性、业务约束、验证与安全要求始终保留。精简与完整技术视图均适用；完整模式增加必要的实施细节，不重复展开同一论证。

1. **结论优先**：先说采用什么设计、用户得到什么变化，再写必要的实现条件。省去“通过分析现有代码”“根据上述分析”“综上所述”等过程性铺垫。先写最终决策；只有影响方案选择的关键理由才用一句话说明。
2. **证据分离**：阅读并核查真实代码、数据库、接口、测试和需求；将来源、事实依据和决策理由保存在 JSON 的 `rules.source`、`rules.basis`、`decisions.rationale` 等对应字段，执行证据与追踪保存在回执/日志/检查报告。精简正文只呈现由这些依据支持的结论和必要限定，不粘贴文件路径、检索过程、完整日志或逐步分析过程。需要复核时以已有 ID 找到依据，不另造重复的证据文档。完整技术模式也只在对应技术项中给出相关依据，不罗列无关发现。
3. **信息唯一**：一个业务结论只在一个主要位置表达。摘要写总决策；要点补充不同的业务规则、实施变化或关键约束；待确认项只写尚需确认的问题及其影响。不要在摘要、规则、图注、风险、验收和结尾用不同措辞反复复述。机器模型保留必要的 ID 引用和验收表达，不因正文去重丢失结构化信息。
4. **图文互补**：图负责关系、流程、状态和时序；文字负责图中不易表达的条件、例外、限制和待决策问题。图注只点明读图目的，避免逐节点复述，也避免把整段正文复制进图。简单变化无需绘图。
5. **增量表达**：只展示本次新增、修改和受影响的行为、接口、数据与依赖。复用的模块只说明复用方式及需要遵守的约束；无变化的既有设计无需重述。删除通用背景、空泛优势、常规建议和无关技术选型。
6. **决策导向**：每项内容必须帮助读者确认业务行为、选择方案、实施或验收。关键业务条件、异常、权限、安全、真实验证状态以及可能改变结论的风险、假设与待确认事项必须保留；未确认内容使用明确的条件或待定标记，不当成已确认事实。

按“总决策 → 按业务流程/依赖排列的独立变化 → 必要图示与技术条件 → 待确认事项”的逻辑组织信息。对同一主题相邻合并，每个要点只讲一个主结论，标题采用具体的业务对象/行为，正文使用短句、主动表达和具体条件。待确认事项在现有独立区域集中展示；无需强制为每种信息增加一节。

**交付前编辑检查（必须执行）**：逐条核对正文结论是否有模型引用、是否与依据一致、是否有读者需要知道的新信息；删掉分析过程、重复证据和重复结论；确认图文互补、顺序自然、边界与不确定性清楚。优先重写合并而非机械删字。处理校验器报告的 `review-repeat` 重复警告；确因不同语境需要保留时，在机器资料中记录理由。该检查只发现部分确定的重复句，语义重复和逻辑清晰度仍需人工/Agent 复核，不能把校验通过当成表达质量已证明。聊天只交付结论、关键待确认项、验证摘要及文件链接/预览；已由图片清楚展示的细节不再逐项复述。

## 默认用法

用户日常只需提供需求，例如：

```text
$visual-explainer 方案：为现有任务列表增加按状态筛选。
```

把下列约定作为此模式的默认值；用户明确指定的路径、范围、格式和回复详略优先。

- **项目上下文**：读取当前业务项目相关代码、接口、数据库定义/迁移、测试和约束，按真实来源区分事实、假设和待确认事项。技能目录用于查阅规则和执行 CLI，输出目录相对业务项目根目录。
- **交付位置**：写入 `docs/design/<name>.design.json`、`docs/design/<name>.html`、`docs/design/<name>.html.checks.json`；截图由 CLI 放在同名 `.html.screenshots/`。从需求选择简短、稳定的文件名，新方案避开无关文件；迭代既有方案先读原 JSON，保留路径和 ID。
- **默认范围**：进行方案设计，修改范围限于本次方案产物。若用户明确授权实施，按其授权继续执行相应工作。
- **方案内容（默认精简）**：先应用六条表达规范，再落实五项设计规则；正文只展示核心结论、关键改动与规则、必要技术条件、待确认事项及 0–2 张核心图。完整且与本次变更相关的技术模型、来源、验收和追踪保存在 JSON/检查报告；不在 HTML 中重复或折叠堆放。明确要求“完整技术方案”才采用完整视图。
- **验证**：执行 `validate --phase design`、`render --view compact --browser`、`deliver <HTML> --spec <JSON> --view compact`（完整技术方案用 `--view full`），修复结构及静态页面错误，尝试真实浏览器检查。浏览器缺失或受限时记录 `skipped` 和原因；新方案的业务验收默认 `not-run`，四类验证状态分别报告。
- **对话预览（默认）**：在最终 HTML 的结构、静态和浏览器检查全部通过后，运行本技能 `software-design/chat-preview.mjs`，从当前 HTML 截取一张含核心方案和待确认事项的摘要图及最多两张不同类型的关键设计图，优先流程图和上下文图。图片保存在同名 `.html.screenshots/` 目录，文件名包含图片内容摘要；宽度或高度超限的图保留在完整 HTML 中，避免缩成难以阅读的长图。只使用本次命令返回的 `images`，不要引用旧图或整页长截图。用户明确不需要预览时跳过此步骤。
- **聊天交付**：默认将本次预览结果中 `images[].markdown` 的每一项作为独立的 Markdown 图片直接写进最终回复（不要放进代码块，也不要仅使用读取图片的工具调用），另给 HTML/JSON/检查报告三个文件链接或路径。文字仍默认不超过 8 行，包含简短结论、关键待确认事项和验证摘要。对话中展示的是静态 PNG；完整方案及可操作交互仍在 HTML。默认不自动打开浏览器。预览状态为 `partial` 时仅展示返回的有效图片；`skipped` 或 `failed` 时简要说明原因并保留 HTML 链接。宿主不支持本地图片渲染时提供对应 PNG 文件链接；不启动 HTTP 服务、不上传项目图片、不声称已成功显示。预览生成状态不等于业务验收通过。用户要求详细解释时按其要求展开。

支持注册本目录命令的宿主也可以使用 `/generate-software-design <需求>`。在 Codex 中优先使用显式 `$visual-explainer 方案：<需求>`；命令注册能力由宿主决定。

## 精简与完整模式

- 默认使用 `init --view compact` 生成最小示例，以实际需求替换示例内容。保留所有模型集合的数组键，但未涉及的术语、接口、数据、状态、风险、质量指标和图可以留空；只建本次变化及其必要依赖。完整性来自真实需求覆盖，不靠填满章节。
- 默认 `review.points` 为 1–6 个核心要点，每项包含 `title`、`text`、`refs`。覆盖全部需求；每项优先一句话/短规则，合并重复的需求、规则、设计和验收描述。明确现状与拟修改，避免长篇代码路径、全量字段、通用风险、常规操作和无变化的既有 API 罗列。
- `scope.assumptions` 仅保留实际待确认事项（最多 5 项），涉及未确认规则的 ID 应在评审要点中关联。不得为满足长度上限隐去影响决策的条件；合并表达或明确请求完整视图。
- `review.diagramIds` 选择 0–2 张核心图，简单需求无需强制绘图；状态变更仍需在技术模型中覆盖全部迁移。优先少节点、短标签、一图一目的，避免图表重复叙述正文。
- 正文（标题、摘要、要点、待确认事项、核心图标题和说明）按必要信息决定长度，不设最低字数或填充目标；几十字能说清的需求就用几十字。800 非空白字符仅为自动校验上限。超限时重新归纳，不截断文字、不删必要模型或伪造通过。正文不得嵌入完整模型、追踪矩阵或隐藏的技术附录。
- 用户明确要求“完整技术方案”时，使用 `init --view full`、`render --view full`，按实际复杂度输出必要技术章节。现有带 review 的模型亦可渲染完整视图；需要补齐实际技术细节时先完善模型。旧模型默认沿用完整视图，既有文件保持兼容；要求精简旧方案时在原 JSON 中添加 review 并重渲染，保留原 ID。
- 默认精简评审与完整技术视图共用模型校验和真实证据。检查报告记录完整追踪关系；精简 HTML 检查显示范围内的要点、待确认事项和所选图。禁止手改生成的 HTML 另造精简首页。

## 五项规则

### 1. 先明确方案，再生成页面

读取需求原文、现有模块、接口、数据库迁移、测试与部署约束。为已确认的事实标明真实文件/行号、版本或需求来源。把推断和待确认事项放入 `scope.assumptions`，业务规则标注 `basis: fact|assumption|decision` 与 `source`。缺少信息时先完成可确定部分，关键阻塞问题集中列出，避免编造业务结论。

按实际变更建模：需求、规则、相关组件和验收必备；术语、接口、数据、状态、质量目标、取舍、风险及迁移/回滚/监控只在相关时建模。复用已有设计时只引用关键约束，避免重新描述整套系统。质量指标一旦声明必须有可测量目标和验收方法；没有变化的集合留空。完整模式保留原模板约定。

### 2. 一份结构化来源，稳定 ID 双向追踪

以 `<name>.design.json` 为唯一事实源。先改源，再重新生成页面；通过源码管理保留变更记录。ID 一经创建保持稳定，不因排序和措辞调整重新编号。

链路为 `REQ → BR → DIAG/API/DATA → AC`。每条需求绑定规则与验收；每条验收反向绑定需求。接口和状态转换绑定规则，同一需求下的验收同时引用接口/状态转换及对应规则，避免跨需求借用验收覆盖。使用确定性校验器检查重复 ID、悬空引用、缺失覆盖及双向关系；校验器输出不等于业务负责人确认。

结构定义和字段详见 `software-design/CONTRACT.md`；`software-design/schema.json` 可用于编辑器补全，语义校验以 `cli.mjs validate` 为准。模板为 `templates/software-design.json`，其中内容全部是待替换的订单示例。

### 3. 术语、接口与状态共用定义

在 `terms` 定义业务词汇，在 `components` 定义职责，在 `data/states/transitions/apis` 定义规范模型。图中引用这些 ID；由渲染器读取名称、接口方法/路径和状态事件。上下文图和时序图的 API 调用箭头指向接口所属组件；返回消息用 label 加 refs 表达。禁止在图中覆盖已引用元素的名称。临时流程动作可使用独立文字节点。

每个状态实体具有唯一初始状态、可达状态和明确的转换条件/动作。保留合法自循环，检查终态的出边和跨实体转换。接口和验收通过 ID 引用同一状态/转换。自动检查保证已建模引用的一致性；自然语言中的同义词、业务遗漏和错误判断仍需结合代码及领域知识审核。

### 4. 将检查记录为可审阅证据

验收状态仅使用 `not-run / skipped / passed / failed`。设计阶段默认 `not-run`，跳过必须解释原因。声明执行成功或失败时，提供显式执行命令产生的回执和日志；回执绑定验收 ID、方案摘要、命令参数、工作目录、时间、退出码、信号和日志摘要。

为每条验收运行能够实际检查其 Given/When/Then 的测试。仅编译、仅生成页面、空测试或展示 `built` 不满足业务验收。校验器能验证回执一致性，测试是否充分覆盖行为需要评审。修改方案正文后旧回执失效；修改实现、环境或依赖后主动重跑相关检查。回执是本地可审阅记录，不能代替受信任 CI 的执行证明。

### 5. 检查最终 HTML

使用离线单文件 HTML；图为内联 SVG；字体使用本地中文字体。保留正文来源超链接，页面呈现不依赖 CDN。检查 ID、锚点、图数量、可访问标签和资源依赖，并在 390/1280 宽度检查页面溢出、图中文字、脚本错误和外部请求。浏览器不可用或检查未执行时如实标记，不能计为通过。结合截图人工复核实际中文字形；系统字体差异不能仅靠尺寸检查确认。

HTML、同名 `.checks.json` 和源码应一起交付。区分方案结构检查、业务验收执行、静态页面检查、浏览器检查四类状态。静态检查通过且业务未执行时，可以交付设计稿；正式宣称验收通过必须满足对应门槛。

## 图的选择

按问题选图，保持每张图一个目的。复杂图拆分成多个视图，使用稳定 ID 关联。序列图最多 5 个参与者，其他图最多 12 个节点；内容超出时拆图，保留原标签。

| 要对齐的内容 | 类型 | 建模要求 |
|---|---|---|
| 谁负责什么、与哪些外部系统交互 | `context` 系统边界/职责图 | 节点引用 COMP；边标明调用、读写或事件 |
| 分支、规则及异常处理 | `flow` 业务流程图 | 规则节点引用 BR；分支标明条件 |
| 调用顺序、事务、重试、异步路径 | `sequence` 时序图 | 参与者引用 COMP；接口消息引用 API；不同异常可拆图 |
| 生命周期、合法/非法转换、幂等事件 | `state` 状态图 | 节点引用 STATE，边引用 TR；显示自循环 |
| 持久化实体、键和关联 | `er` 数据关系图 | 节点引用 DATA，标明关联字段与基数；约束写入 DATA |

有状态变更必须有覆盖全部已声明 TR 的状态图。根据需求增加部署图、权限矩阵、页面原型等独立补充物时，仍从同一模型取名并在方案中说明边界。此版本的生成器支持表中五类图。

## 工作步骤

1. 读取真实输入，记录来源和未决事项。既有方案升级时先读原 JSON，保留 ID。
2. 从精简模板创建 JSON，替换全部示例业务内容；先建立 businessFlow 场景和状态快照，再建接口/数据/规则与验收，最后设置 review.points 和 review.diagramIds。完整模式按需采用原模板。逐项建立需求、规则、模型及验收关系。
3. 根据上表绘图，复核正常/失败/重试/并发/超时/回滚路径，确定各项质量目标。
4. 按六条表达规范复核并压缩评审正文：删过程、分离证据、合并重复结论、调整信息顺序。执行 `validate --phase design`，修复结构和引用错误；处理 `review-repeat`，其他 warnings 给出实际解释或消除对应问题。
5. 执行 `render --view compact --browser`（完整模式用 `--view full`），查看生成页面和检查报告。浏览器可用时检查截图；发现问题先修正方案 JSON 后重跑。若问题来自生成器，记录故障与受影响产物，按用户授权处理工具修复。环境不能运行浏览器时报告 `skipped`，保留可复查页面。
6. 执行 `deliver <HTML> --spec <JSON> --view compact`（完整模式 full），门禁未通过不得交付为标准方案。通过后按默认对话预览规则执行 `node "<skill-dir>/software-design/chat-preview.mjs" "<实际 HTML 路径>"`，如渲染时指定了 `--browser-executable`，此处沿用。根据实际结果内嵌 PNG 并交付 HTML、JSON、检查报告位置、关键未决事项和验证状态。用户已授权实施时继续完成实施；仅要求方案时等待实际业务决策。
7. 实施完成后针对 AC 执行测试并记录回执，更新 `verification`，执行 `validate --phase delivery`、`render --phase delivery --require-browser` 和 `deliver --phase delivery`（补全 HTML、--spec、--view 参数）。

## 命令与证据

以下命令在业务项目根目录执行；先将 `<skill-dir>` 替换为本技能 `SKILL.md` 所在的绝对目录，将示例 `order` 替换为本次方案名称。Node >=20，初始化、建模、渲染和静态检查无需安装新依赖。

```bash
node "<skill-dir>/software-design/cli.mjs" init docs/design/order.design.json --view compact
# 编辑 JSON：以真实项目资料替换示例内容
node "<skill-dir>/software-design/cli.mjs" validate docs/design/order.design.json --phase design
node "<skill-dir>/software-design/cli.mjs" render docs/design/order.design.json --out docs/design/order.html --view compact --browser
node "<skill-dir>/software-design/cli.mjs" deliver docs/design/order.html --spec docs/design/order.design.json --view compact
node "<skill-dir>/software-design/chat-preview.mjs" docs/design/order.html
```

浏览器检查可使用环境中的 `playwright` 或 `playwright-core`；已安装的 Chromium 可通过 `--browser-executable <path>` 指定。`--browser` 遇到环境缺失会记录 skipped，`--require-browser` 会返回非零退出码。工具不自动下载浏览器。需要严格交付时安装 Playwright 及 Chromium，然后使用 `--require-browser`。输出浏览器截图置于 `<page.html>.screenshots/`。

显式记录一个真正的业务测试，例如项目已有的 Node 测试（其他语言可替换可执行文件和参数）：

```bash
node "<skill-dir>/software-design/cli.mjs" record docs/design/order.design.json --acceptance AC-repeat --receipt evidence/repeat-001.json --cwd . -- node --test test/order-repeat.test.mjs
```

记录器使用 `shell:false`，命令作为独立参数执行，超时默认 120 秒，可用 `--timeout-ms` 调整。Windows 可直接使用 `node`、`python`、`java` 等可执行程序；脚本包装器如 `.cmd` 需要显式调用其解释器。运行失败也会留下回执。每次使用新回执路径，避免覆盖历史记录。

检查日志后更新对应 AC：

```json
"verification": {"status": "passed", "receipt": "evidence/repeat-001.json"}
```

回执路径相对于设计 JSON 所在目录，日志也位于该目录树内。记录器不会自动修改验收结论。`render` 从不执行 JSON 中的命令；只有显式 `record ... -- <command>` 才运行测试。分发带证据的源文件时保留其相对目录结构，发布前检查日志是否含敏感内容。

## 交付边界

- `design`：结构、引用、覆盖和已有执行声明可验证；允许明确标注的待确认事项及未执行验收。
- `delivery`：额外要求所有 must 需求关联验收和所有质量指标关联验收具有有效 passed 回执；浏览器是否必需由 `--require-browser` 独立约束。
- 页面静态校验覆盖本生成器的 HTML 契约；浏览器检查补充实际 DOM 和布局验证。业务决策、代码正确性及测试充分性由对应来源、测试与评审共同确认。
