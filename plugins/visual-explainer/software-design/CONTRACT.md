# Software design profile v1 — source format and module contract

This file is the compact machine-source reference. All modules in this directory are an opt-in extension; upstream kit/plan code stays untouched. Node >=20, standard library only (optional Playwright for browser inspection).

## JSON source

Root: `schemaVersion: 1`, `id` (DESIGN-*), `title`, `summary`, `language: "zh-CN"`, `scope: {goals: string[], in: string[], out: string[], assumptions: string[]}`, `terms`, `components`, `requirements`, `rules`, `data`, `states`, `transitions`, `apis`, `diagrams`, `acceptance`, `decisions`, `risks`, `quality`, `delivery`.

All collections are arrays. IDs are global, stable, ASCII `[A-Za-z0-9_-]+` with the prefixes below. References are case sensitive. Each item has a `title` except states (`name`) and terms (`name`). No HTML is trusted. Plain text is escaped. Additional metadata is permitted but never treated as executable instructions.

- terms: `{id: TERM-*, name, definition}`
- components: `{id: COMP-*, title, responsibility, kind: "actor"|"service"|"external"|"store"}`
- requirements: `{id: REQ-*, title, text, priority: "must"|"should"|"could", ruleIds: BR-[], acceptanceIds: AC-[]}`
- rules: `{id: BR-*, title, text, refs: ID[], basis: "fact"|"assumption"|"decision", source: string}`. Source identifies actual document/code location or explicitly states pending confirmation; do not invent evidence.
- data: `{id: DATA-*, title, termId: TERM-*, fields: [{name, type, required: boolean, description}], constraints: string[]}`
- states: `{id: STATE-*, dataId: DATA-*, name, initial: boolean, terminal: boolean}`
- transitions: `{id: TR-*, title, from: STATE-*, to: STATE-*, event, guard, action, ruleIds: BR-[]}`. Self loops allowed. Cross-entity transitions rejected.
- apis: `{id: API-*, title, method, path, owner: COMP-*, ruleIds: BR-[], dataIds: DATA-[], transitionIds: TR-[], request: string, response: string, errors: [{code, condition, handling}]}`
- diagrams: `{id: DIAG-*, title, type: "context"|"flow"|"state"|"sequence"|"er", purpose, nodes: [{id, ref?: ID, label?: string}], edges: [{id, from: nodeID, to: nodeID, label?: string, apiId?: API-*, transitionId?: TR-*, refs?: ID[]}]}`. Node IDs and edge IDs are scoped to one diagram. Use ref OR label; canonical ref labels come from the shared model and cannot be overridden. State nodes reference STATE; each state edge has transitionId matching its canonical from/to. Sequence/context participants reference COMP; an apiId call edge targets the owning COMP (responses use label plus refs); ER nodes reference DATA. API/transition edge labels are derived; do not override with label. Sequence edges are ordered messages, at most 5 participants. Other graphs at most 12 nodes. No silent truncation of labels.
- acceptance: `{id: AC-*, title, given, when, then, requirementIds: REQ-[], refs: ID[], verification: {status: "not-run"|"skipped"|"passed"|"failed", reason?: string, receipt?: string}}`. Receipts are relative to the source JSON's directory. A skipped check needs a reason. A passed/failed check needs a verified receipt. Business checks remain not-run in design examples.
- decisions: `{id: DEC-*, title, options: string[], choice, rationale, refs: ID[]}`
- risks: `{id: RISK-*, title, impact, mitigation, owner, refs: ID[]}`
- quality: `{id: NFR-*, title, target, measurement, acceptanceIds: AC-[]}`
- delivery: `{implementation: string[], migration: string[], rollback: string[], monitoring: string[]}`. Use an explicit justified not-applicable statement where relevant; never silently omit.

## Business-flow contract (required for new checked handoff)

Legacy v1 models remain readable/renderable; `deliver` requires `businessFlow:{version:1,intent:"current"|"target",scenarios:[...]}`. For an existing-process audit use current; target proposals can include separately labelled current context. A scenario is `{id:SCN-*,title,phase:"current"|"target",kind:"main"|"exception",highlight?:boolean,result:"success"|"rejected"|"pending"|"failed",actorId:COMP-*,trigger,condition,steps:[{actorId:COMP-*,action,ruleIds:BR-[],apiIds:API-[],transitionIds:TR-[]}],outcome,requirementIds:REQ-[],acceptanceIds:AC-[],startStateIds:STATE-[],endStateIds:STATE-[]}`. Main paths and highlighted exceptions appear in compact HTML; all paths appear in full HTML. Scenario text counts toward the compact budget. Model only the actual relevant changes, do not add filler. Each path has its own guards and outcome; identical normalized phase, trigger actor, trigger text, condition and start-state vector cannot define multiple competing paths; current facts cannot use proposed decision rules. Each requirement has a path for the requested intent; all rules/APIs/transitions must appear in paths. Each path's ACs must cover its referenced rules and API/transition relationships.

Every stateful DATA item declares `lifecycleField` matching one actual field; separate independent status objects even if physically stored in one table. Start/end snapshots contain at most one state per DATA and may be empty for stateless paths. Replay each step's transitions in order; the start must match current state and the final vector must match the declared result. A step linking API and TR must use a transition declared by that API; use a separate internal step if appropriate. State diagrams contain one DATA object, `phase:current|target`, and all transitions used in that phase must be drawn. Context/ER diagrams retain existing checks. Flow diagrams require `scenarioId` and the exact canonical nodes/edges from `cli.mjs flow <spec> --scenario SCN-id` (up to ten steps per drawn path). Sequence diagrams require scenarioId and ordered API calls and caller components exactly matching scenario step calls (for an API step actorId is its caller); non-API messages reference scenario rules/API/TR. Scenario states and conditions are declarations, not execution of production code; source truth, completeness, guards and semantic consistency require human/Agent review.

New `deliver <page.html> --spec <design.json> [--view compact|full] [--phase design|delivery]` checks the enhanced HTML profile, the validated business model, source/HTML hashes, matching successful structure/static report, attempted browser check and current acceptance states; re-renders canonical HTML and rejects differences. It is a local consistency gate, not a signed receipt, runtime security boundary or business approval. It does not force an arbitrary host to invoke the command; the Skill explicitly requires it before checked handoff.

## Compact review (optional)

Add `review: {points: [{title, text, refs: ID[]}], diagramIds: DIAG-[]}` to a v1 model to opt into the compact view. It has 1–6 points covering every requirement by explicit ID, 0–2 distinct selected diagrams, and up to 5 pending items in scope.assumptions. Each assumption rule must be linked by a point and its pending question stated in scope.assumptions. The combined title, summary, point text/titles, pending text and selected diagram title/purpose have a hard 800 non-whitespace Unicode character budget. No silent truncation. The full JSON model and the report retain all technical content and traceability; the compact HTML contains no full hidden appendix or embedded model. Review coverage is mechanical; semantic completeness still requires review. `reviewRepetitionWarnings(spec)` reports `review-repeat` for repeated normalized prose sentences/clauses of at least 16 Unicode characters across or within summary, review point bodies, pending items and selected diagram purposes. It ignores headings, short labels, references and evidence fields; warnings are nonblocking for existing models and are included in the validation/check report. Agents must rewrite needless repetition or document a justified exception. This lint does not establish semantic uniqueness, factual correctness or coherent ordering. Apply the six expression principles in `references/software-design.md` to both views; there is no minimum prose length.

With review present, terms, diagrams, decisions, risks and quality may be empty when irrelevant, and delivery.migration/rollback/monitoring may be empty. Requirements, rules, components, acceptance and actual implementation remain required. A requirement may reach an explicitly linked COMP in addition to DIAG/API/DATA (the report records componentIds for compact models). All supplied references, state transitions, evidence and delivery gates retain the same checks. Legacy models without review retain all original requirements.

CLI: `init <spec.json> --view compact` uses a minimal valid example. `render <spec.json> --out <page.html> --view compact` renders the review; view defaults to compact when review exists, full otherwise. `--view full` renders all model sections. Compact inspection validates selected figures and review markers, while model validation still checks all model relationships. The report includes view, sourceSha256, traceability and compact review metadata.

## Validation / traceability (legacy/full model without review)

Required narrative sections are nonempty; scope.out/assumptions may be empty. terms/components/requirements/rules/diagrams/acceptance must be nonempty. Other model collections may be empty when the design has no such concept. decisions/risks/quality each contain at least one documented entry (a justified no-change risk is valid). Every requirement has rules and acceptance. Requirement↔acceptance backlinks must agree. Each rule is owned by a requirement and covered by an acceptance refs array for that requirement. Each requirement's rule chain must reach at least one diagram (node or edge refs), API, or DATA item. Every API and transition connects to rules. IDs, paths, fields, states, anchors, and edge endpoints must be consistent. Each stateful data entity has one initial state; all states are reachable from it; terminal states have no outgoing transitions. Every transition is shown in a state diagram and covered by an acceptance refs array. Each API and transition is covered for every linked rule and owning requirement: one acceptance must link that requirement bidirectionally and include both the rule and API/transition in refs. Fact basis requires source. Any provided ref is validated even in optional collections. `phase=design` validates structure and coverage, leaves execution pending. `phase=delivery` additionally requires all must requirements' acceptance AND all quality acceptance passed with valid fresh receipts.

These are mechanical checks, not proof that a business requirement is true. Assumptions and stakeholder approval remain explicit.

## Module interfaces

- `model.mjs`: `validateDesign(spec, {phase = "design", evidence = new Map()} = {})` → `{ok, errors: [{code,path,message}], warnings: [{code,path,message}], traceability: [{requirementId,ruleIds,diagramIds,apiIds,dataIds,acceptanceIds}]}`. `evidence` maps AC ID to `{ok, errors: string[], status}` prepared by evidence.mjs; absent receipts fail passed/failed statuses. `indexDesign(spec)` → `Map(id, item)`; `labelFor(item)` → name/title/id.
- `render.mjs`: `renderDesignSource(spec, validation)` → source HTML string with kit marker, local CSS/JS, `<html lang="zh-CN">`, inline SVG diagrams, source data (`script[type=application/json]` with escaped `<`), traceability table, explicit design/business/page-check statuses. No filesystem writes. Uses `diagrams.mjs`, `model.mjs`; no direct core imports.
- `diagrams.mjs`: `renderDiagram(diagram, index)` → accessible SVG string. State self loops preserved, Chinese text wraps, no CDN.
- `upstream.mjs`: the only upstream API imports live here; `renderWithUpstream(source)` → final HTML. Removes only known Google Font links for this opt-in profile, retains kit inlining and comment/reply UI. Fails clearly on incompatible upstream API. No remote fonts.
- `inspect.mjs`: `inspectHtml(html, {spec} = {})` → `{ok, errors: [{code,message}], warnings: [{code,message}]}`; `inspectBrowser(path, {required = false, executablePath, artifactDir} = {})` async → `{status: "passed"|"failed"|"skipped", errors: string[], reason?, screenshots?: string[]}`. Browser check viewport 390/1280, page errors/network resources, document width, SVG text bounds/size, readiness. Must distinguish unavailable browser from pass.
- `evidence.mjs`: records explicit command execution and verifies receipt/log integrity. `cli.mjs`: initializes, validates, renders, inspects, and records evidence.

Receipt v1: `{schemaVersion:1, acceptanceId, specDigest, command: string[], cwd, startedAt, finishedAt, exitCode: number|null, signal: string|null, status:"passed"|"failed", log: relativePath, logSha256}`. `specDigest` is SHA256 of canonical JSON spec excluding ALL acceptance[].verification. `verifyEvidence(spec, baseDir)` checks file containment, logs, hashes, matching AC/digest/status and returns evidence Map. Explicit `record` executes argv with shell:false, records result, does NOT edit spec automatically or run commands from spec. Renderer never executes a business check.

CLI: `node <skill>/software-design/cli.mjs init <spec.json>`; `validate <spec.json> [--phase design|delivery]`; `render <spec.json> --out <page.html> [--phase ...] [--browser] [--require-browser] [--browser-executable <path>]`; `inspect <page.html> [--spec <spec.json>] [--browser] [--require-browser]`; `record <spec.json> --acceptance AC-* --receipt <path-relative-to-spec> [--cwd <dir>] -- <command> <args...>`.
